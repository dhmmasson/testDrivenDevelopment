    TestSuite & Autograder

    The autograder is a Python script provided in the starter pack that runs a test suite against any pandora.jar. It is the primary tool used by both students and the teacher team to evaluate implementations.

    The Autograder

    python test/autograder.py \
  -t <path_test_suite> \
  -m <path_manifest> \
  -f <json|md> \
  -o <output_path> \
  -j <jacoco_agent_path> \
  <pathToPandora>

    Arguments

    Argument Required Description
    <pathToPandora> yes Path to the jar to test (e.g. target/pandora.jar)
    -t <path_test_suite> yes Path to testSuite.json
    -m <path_manifest> yes Path to manifest.json
    -f <json\|md> no Output format: json (machine-readable) or md (Markdown report). Defaults to terminal output
    -o <output_path> no Write results to this file instead of stdout
    -j <jacoco_agent_path> no Path to the JaCoCo agent jar — enables code coverage measurement during the run

    Typical Usage

    Run your test suite against your own jar:

    python test/autograder.py -t test/testSuite.json -m manifest.json target/pandora.jar

    Run your test suite against another team’s jar:

    python test/autograder.py -t test/testSuite.json -m path/to/their/manifest.json path/to/their/pandora.jar

    Save a Markdown report:

    python test/autograder.py -t test/testSuite.json -m manifest.json -f md -o results.md target/pandora.jar

    Run with code coverage:

    python test/autograder.py -t test/testSuite.json -m manifest.json -j ~/.m2/repository/org/jacoco/org.jacoco.agent/0.8.11/org.jacoco.agent-0.8.11-runtime.jar target/pandora.jar

    The script prints a summary grouped by milestone. A passing test is shown in green; a failing test shows the expected vs. actual diff.

    Building Your TestSuite

    You are required to produce Black Box Integration Tests for every feature you implement by filling test/testSuite.json and placing the corresponding flight record files in test/resources/.

    File Format

    test/testSuite.json is a JSON array of test descriptions. There are three kinds of tests: feature tests, metadata tests, and multi-file tests.

    Fields

    Field Type Required Description
    id number yes Unique integer within the suite
    milestone number yes Milestone number, used for grouping output
    mode "feature" | "full" yes feature: run with the appropriate CLI flags; full: generate the full report and parse it for the expected value
    result string | number yes Expected output — the autograder does a strict string comparison
    feature string conditional Exact value passed to -o (e.g. maxAlt, maxAccelG, filenames) — must match the Features table. Required unless metadata is used
    metadata string conditional Metadata key to query via -m (e.g. flight_id, flight_code, origin, date, from, to, motor(s), mass_aircraft, mass_fuel, lift_coef, drag_coef). Required for metadata tests
    file string conditional Path to a single flight record, relative to the project root. Use this for single-file tests
    files string[] conditional Array of paths to multiple flight records. Use this instead of file when the test requires more than one input file

    You must provide either file (single file) or files (multiple files), but not both.

    You must provide either feature or metadata, but not both.

    Follow the output format rules precisely — decimal separator, number of digits, and units must all match exactly.

    Examples

    Feature test (single file, feature mode)

    Tests a specific feature on one flight record using -o <feature>:

    {
  "id": 1000536,
  "milestone": 3,
  "mode": "feature",
  "feature": "maxAccelG",
  "file": "./test/testsFiles/mono/0_501_Tu-142.frd",
  "result": 2.41
}

    Feature test (single file, full mode)

    Runs the full report and checks that the feature value matches:

    {
  "id": 1000535,
  "milestone": 3,
  "mode": "full",
  "feature": "maxAccelG",
  "file": "./test/testsFiles/mono/0_501_Tu-142.frd",
  "result": 2.41
}

    Metadata test

    Queries a metadata field from a single flight record using -m <key>:

    {
  "id": 1001001,
  "milestone": 1,
  "mode": "feature",
  "metadata": "flight_id",
  "file": "./test/testsFiles/mono/0_201_MiG-23MLD.frd",
  "result": "201"
}
    {
  "id": 1001010,
  "milestone": 1,
  "mode": "feature",
  "metadata": "lift_coef",
  "file": "./test/testsFiles/mono/0_201_MiG-23MLD.frd",
  "result": "1.9060340730520209"
}

    Multi-file test

    Tests a feature that takes multiple input files (using files instead of file):

    {
  "id": 1003001,
  "milestone": 1,
  "mode": "feature",
  "feature": "filenames",
  "files": [
    "./test/testsFiles/mono/0_201_MiG-23MLD.frd",
    "./test/testsFiles/US/0_601_F-14A.frd"
  ],
  "result": "0_201_MiG-23MLD.frd\n0_601_F-14A.frd"
}

    What Makes a Good TestSuite

    • At least one test per feature and per CLI option you have implemented
    • Feature mode tests: use a hand-crafted flight record where the correct answer is easy to verify by hand (e.g., 10 records all at 1000 m → avgAlt must be 1000.00)
    • Varied inputs: different aircraft, different flight profiles, edge cases (short flight, single record, missing optional columns)
    • Discriminating tests: your suite should catch bugs in other teams’ implementations — if a team doesn’t handle negative temperatures, your suite should fail them

    Place hand-crafted flight records in test/resources/ alongside the provided files. See Integration-Test for guidance on designing test records.
